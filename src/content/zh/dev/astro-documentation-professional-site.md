我选择 [Astro](https://astro.build/)，因为这个网站的主要内容是文字。对于应该加载迅速、方便编辑的页面，我不需要厚重的应用框架。

这听起来简单，却是最主要的决策。职业个人网站应当让读者容易找到个人介绍、精选项目、技术笔记和少量个人写作。除非内容需要，否则不必做成完整的应用。

Astro 的静态优先方式很适合这里。文章放在 Markdown 文件中，[内容集合](https://docs.astro.build/en/guides/content-collections/)为文件提供轻量的数据模型，页面可以共用布局，也不必全部变为客户端应用。

本站将内容分为技术与随笔：

```text
src/content/dev
src/content/journal
```

技术栏目专注实践笔记，随笔保留精选个人文章与思考。这能避免首页变成大档案库，也让读者直接选择感兴趣的内容。

内容集合虽小，却建立了真实的边界。文章可以要求标题、描述、日期、标签、分类和草稿状态，在发布前发现错误。

```yaml
---
title: "文章标题"
description: "简短实用的摘要。"
date: 2025-10-31
author: "Jiyu Yan"
categories: ["Engineering"]
tags: ["Astro", "Writing"]
draft: true
---
```

`draft` 很重要：未完成的文章可以沿用正式发布时的结构，同时不出现在公开网站上。

我喜欢 Astro 的另一个原因是网站可以扩展，而不会变成堆放所有内容的地方。内容模型不能替代筛选，但能让筛选容易些。技术文章可以短而实用，个人随笔则保持独立，不冲淡网站的职业信息。

这也适用于产品文档。好文档需要结构、命名、归属，以及避免链接失效和元数据过期的方法。个人网站规模更小，但同样的习惯仍有价值。

取舍在于 Astro 不打算包办一切。需要高度交互的仪表盘、实时协作或复杂登录流程时，我会选择其他应用结构。对于写作与文档，这个限制反而有利于专注。

我也喜欢它不会默认把每个组件放到客户端。大部分页面保持 HTML，确实需要 JavaScript 的交互再按需加入。

这个网站的方案平实而合适：静态优先、Markdown 内容、集合约束、简单导航，以及经过筛选的写作，而不是整站导入旧档案。

价值不在于技术栈听起来新，而在于维护容易，职业信息表达得更清楚。
